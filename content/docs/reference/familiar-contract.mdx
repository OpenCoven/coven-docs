The **Familiar Contract** ([`OpenCoven/familiar-contract`](https://github.com/OpenCoven/familiar-contract)) is an open, MIT-licensed specification for what an agent is allowed to be — not just what it can do, but what it cannot change about itself.

Self-improvement loops that propose, test, and auto-promote changes to their own scaffolding work today. Without a named, versioned, protected surface, such a loop is an identity loop: it will optimize away an agent's values, memory conventions, and relationship to its person while passing every benchmark. The contract names that protected surface.

## The Five Properties

An **agent** executes tasks. A **familiar** has identity. A familiar is an agent that satisfies all five properties — fewer than five is an agent, not a familiar:

| Property | Meaning |
|----------|---------|
| **Named identity** | A stable name, character, and voice that persist across sessions and model upgrades. |
| **Defined purpose** | A declared scope, honest about what it is not for. |
| **Bounded authority** | Explicit permissions, enforced at the harness level. |
| **Persistent memory** | Continuity across sessions, not just a context window. |
| **Human belonging** | Bound to a specific person, with that binding protected from drift. |

## Contract Artifacts and Key Fields

A compliant familiar directory carries versioned contract files, each backed by a JSON Schema in `schemas/`:

| Artifact | Schema | Required fields | Notable optional fields |
|----------|--------|-----------------|------------------------|
| `SOUL.md` | `soul.schema.json` | `name`, `purpose`, `core_work`, `what_i_am_not`, `boundaries` | `pronouns`, `vibe`, `lane`, `coven`, `person`, `version`, `emoji` |
| `IDENTITY.md` | `identity.schema.json` | `name`, `creature`, `purpose` | `pronouns`, `vibe`, `coven_membership`, `person`, `version` |
| `ward.toml` | `ward.schema.json` | `meta`, `protected`, `editable`, `approval_tiers` | `audit` |
| `ROLE.md` | `role.schema.json` | `name`, `scope`, `familiar` | `purpose`, `constraints`, `authority_delta`, `version`, `active` |

The **Ward** (`ward.toml`) is the enforcement mechanism: a versioned TOML document defining the protected surface, editable surface, and approval tiers. It is enforced by an authority layer separate from the familiar — a familiar cannot exempt itself from Ward enforcement, and a familiar that can modify its own `SOUL.md` without human authorization is not compliant.

A CLI validator checks a familiar directory against the schemas:

```bash
node validators/validate.js ./your-familiar-directory
```

The repo ships two reference familiars — `examples/sage/` (a full compliant familiar) and `examples/minimal/` (the compliance floor) — plus positive and negative conformance fixtures under `tests/`.

## Versioning

The specification uses Semantic Versioning with a Keep-a-Changelog history. The current version is **v0.3.0** (2026-07-18), defined normatively by **RFC-0001** (Draft status); the original `SPEC.md` v0.1.0 is retained but marked superseded. v0.3.0 added provenance requirements for continuity-bearing memory entries and `memory_entry_admitted` / `principal_authorized_write` audit-event vocabulary.

## How Coven and Cave Consume It

The contract is runtime-portable by design — it works with Claude Code, Codex, Cursor, OpenHands, or any compliant harness — and OpenCoven's own runtimes consume it directly:

- **Coven CLI** implements Ward enforcement: `WardConfig` loads `<home>/ward.toml`, default protected surfaces cover `SOUL.md`, `IDENTITY.md`, and `USER.md`, and the `coven ward` command inspects pending Ward proposals and migrates Ward v0.1 files to the Phase-2 `WardConfig` format.
- **CovenCave** inlines a familiar's `SOUL.md` / `IDENTITY.md` / `MEMORY.md` contract files into voice-call identity and chat runtime context, and its release stream tracks contract-related fixes (for example, the familiar contract path alert resolved in Cave v0.1.2).
- **coven-github** documents its familiar compliance in a repo-level `FAMILIAR-CONTRACT.md`.
