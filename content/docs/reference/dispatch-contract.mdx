# Dispatch contract

The contract for message and task dispatch between the orchestrator and familiars,
and for replies back. The bus guarantees **at-least-once delivery** and
**per-stream FIFO ordering**; everything stronger (exactly-once, global order) is
a *consumer property* built on top, not a transport feature.

## Delivery guarantees

| Level | Meaning | Use when |
|---|---|---|
| **At-most-once** | Sent 0–1×. May be lost, never duplicated. | Fire-and-forget pings, presence, telemetry — loss is cheap, replay is harmful. |
| **At-least-once** | Sent 1+×. Never lost, may duplicate. | Task dispatch + result replies. **Default.** Pair with idempotency. |
| **Exactly-once** | Effectively 1×. | Never promise it on the wire — emulate it: at-least-once delivery + dedupe on a stable `msg_id` at the consumer. |

**Rule:** the bus guarantees at-least-once. Exactly-once is a *consumer property*,
achieved by dedupe — not a transport feature.

## Ordering guarantees

| Scope | Guarantee |
|---|---|
| Per (sender → recipient) stream | **FIFO.** Monotonic `seq` per stream; recipient rejects/buffers gaps. |
| Across recipients | **None.** No global order. Don't assume familiar A saw msg N before familiar B. |
| Replies back | Ordered per task by `seq`; correlate to dispatch via `correlation_id`, not arrival time. |

## Message envelope

The minimum fields to make the guarantees above hold.

```jsonc
{
  "msg_id":         "ULID",   // dedupe key, stable across retries
  "correlation_id": "ULID",   // ties reply → originating dispatch
  "stream_id":      "string", // (sender, recipient) — FIFO domain
  "seq":            0,         // monotonic within stream_id
  "attempt":        0,         // retry counter; >0 means "possible dup"
  "deadline":       "RFC3339"  // drop if past; bounds at-least-once retries
}
```

## Dispatch rules (orchestrator → familiar)

1. Assign `msg_id` once; **reuse it on every retry** (else dedupe can't work).
2. Retry until ack or `deadline`. After deadline → dead-letter, surface to the orchestrator.
3. Familiar **acks on durable receipt**, not on completion. Completion is a separate reply message.
4. Replies carry the dispatch's `correlation_id`; the orchestrator matches on that, never on order-of-arrival.
5. Every handler is **idempotent** on `msg_id` — at-least-once means dups *will* happen.

## Failure semantics

- **No ack before deadline:** retry (same `msg_id`), then dead-letter. Never silently drop.
- **Gap in `seq`:** buffer and wait, or request resend — never process out of order.
- **Duplicate `msg_id`:** ack again (idempotent), do not re-execute.

**Bottom line:** at-least-once + per-stream FIFO + consumer-side dedupe. Don't
promise exactly-once or global ordering — neither survives a partition.
