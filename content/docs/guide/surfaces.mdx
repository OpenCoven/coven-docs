OpenCoven's first-party surfaces fall into three groups: **UI surfaces** you sit in front of, **channel connectors** that deliver familiar output to chat platforms, and **CLI observability views** that read coven state without changing it. The UI surfaces are not competing products: every one of them is a client of the same local Coven daemon, the same session ledger, and the same `/api/v1` socket contract. Choosing a surface changes how you see your familiars and sessions — never what the daemon enforces.

## Quick decision guide

- **"I want to run one agent task from my shell."** Use `coven run codex "fix the failing tests"` — the [CLI](/docs/cli/run) is the shortest path.
- **"I want to pair with a coding agent in my terminal."** Use [Coven Code](/docs/coven-code): `coven tui` or `coven-code`.
- **"I want to talk to my familiars and watch what they do."** Use [Cave](/docs/guide/cave), the desktop home.
- **"I want visible panes, diffs, and review around agent sessions."** Use [CastCodes](/docs/guide/cast-codes) and the [demo loop](/docs/guide/demo-loop).
- **"I am scripting or building a client."** Skip all of the above and speak to the [socket API](/docs/daemon/socket-api) directly.

You can switch UI surfaces at any time. A session launched from the CLI is visible in CastCodes and Cave, because there is only one daemon and one ledger underneath.

## Channel connectors

Channel connectors let familiars post to chat platforms. They are delivery adapters, not session clients: they send outbound messages through platform bot APIs and never launch, attach to, or control daemon sessions.

Both connectors ship in the `@opencoven/channels` package, read bot tokens through 1Password references (never raw tokens in config), and let callers address targets by raw IDs or logical target names. See [Channels](/docs/reference/channels) for setup and configuration.

## CLI observability surfaces

The `coven` CLI also ships a set of read-only observability commands: `coven status`, `coven familiars`, `coven skills`, `coven memory`, `coven research`, `coven calls`, and `coven hub status`. Each renders through the same in-process API router the daemon socket uses, so `--json` output carries exactly the body the daemon serves for the same route — one source of truth for shapes. They are offline reads over `~/.coven` files and the SQLite store, and the Cast shell and chat UI reuse the same views, so every surface renders the same data the same way.

See [Observability commands](/docs/cli/observe) for each command and its output.

## How `coven` and `coven-code` relate

<Callout type="warn" title="One command, two binaries">
The bare `coven` command ships with `@opencoven/cli` (the daemon CLI). The `coven-code` binary ships separately with `@opencoven/coven-code` (the coding TUI). When `coven-code` is on `PATH`, interactive `coven` and `coven tui` invocations exec into Coven Code automatically. Set `COVEN_LEGACY_TUI=1` to opt out and keep the legacy TUI.
</Callout>

Explicit subcommands such as `coven run`, `coven daemon`, and `coven sessions` always belong to the daemon CLI regardless of what is on `PATH`. Only the interactive entry point hands off. If a surface behaves unexpectedly, check which binary answered with `coven doctor` and see the [Coven Code install notes](/docs/coven-code/install).

Local state is split the same way:

| Directory | Owner | Contents |
| --- | --- | --- |
| `~/.coven` (or `$COVEN_HOME`) | Coven daemon | Socket, SQLite session ledger, daemon metadata. |
| `~/.coven-code` | Coven Code | TUI settings, provider accounts, prompts, keybindings. |

## What never changes between surfaces

Every UI surface is a client. None of them can widen the authority boundary:

- The daemon validates project roots, working directories, harness ids, and session liveness for every request.
- Provider credentials stay with harnesses and Coven Code's own auth store — no surface proxies them through the daemon.
- Session history is recorded once, in the daemon ledger, no matter which surface launched the work.
- Channel connectors stay outbound-only delivery adapters; they read bot tokens through 1Password references and hold no daemon authority.

See the [authority rule](/docs/guide/cast-codes#authority-rule) and [daemon security](/docs/daemon/security) for the enforcement details.
