OpenCoven ships several first-party surfaces. They are not competing products: every one of them is a client of the same local Coven daemon, the same session ledger, and the same `/api/v1` socket contract. Choosing a surface changes how you see your familiars and sessions — never what the daemon enforces.

## Quick decision guide

- **"I want to run one agent task from my shell."** Use `coven run codex "fix the failing tests"` — the [CLI](/docs/cli/run) is the shortest path.
- **"I want to pair with a coding agent in my terminal."** Use [Coven Code](/docs/coven-code): `coven tui` or `coven-code`.
- **"I want to talk to my familiars and watch what they do."** Use [Cave](/docs/guide/cave), the desktop home.
- **"I want visible panes, diffs, and review around agent sessions."** Use [CastCodes](/docs/guide/cast-codes) and the [demo loop](/docs/guide/demo-loop).
- **"I am scripting or building a client."** Skip all of the above and speak to the [socket API](/docs/daemon/socket-api) directly.

You can switch surfaces at any time. A session launched from the CLI is visible in CastCodes and Cave, because there is only one daemon and one ledger underneath.

## How `coven` and `coven-code` relate

<Callout type="warn" title="One command, two binaries">
The bare `coven` command ships with `@opencoven/cli` (the daemon CLI). The `coven-code` binary ships separately with `@opencoven/coven-code` (the coding TUI). When `coven-code` is on `PATH`, interactive `coven` and `coven tui` invocations exec into Coven Code automatically. Set `COVEN_LEGACY_TUI=1` to opt out and keep the legacy TUI.
</Callout>

Explicit subcommands such as `coven run`, `coven daemon`, and `coven sessions` always belong to the daemon CLI regardless of what is on `PATH`. Only the interactive entry point hands off. If a surface behaves unexpectedly, check which binary answered with `coven doctor` and see the [Coven Code install notes](/docs/coven-code/install).

Local state is split the same way:

| Directory | Owner | Contents |
| --- | --- | --- |
| `~/.coven` (or `$COVEN_HOME`) | Coven daemon | Socket, SQLite session ledger, daemon metadata. |
| `~/.coven-code` | Coven Code | TUI settings, provider accounts, prompts, keybindings. |

## What never changes between surfaces

Every surface is a client. None of them can widen the authority boundary:

- The daemon validates project roots, working directories, harness ids, and session liveness for every request.
- Provider credentials stay with harnesses and Coven Code's own auth store — no surface proxies them through the daemon.
- Session history is recorded once, in the daemon ledger, no matter which surface launched the work.

See the [authority rule](/docs/guide/cast-codes#authority-rule) and [daemon security](/docs/daemon/security) for the enforcement details.
